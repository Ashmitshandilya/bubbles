# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

Bubbles is a chat-first longitudinal health-intelligence prototype. It combines structured health observations, deterministic safety triage, evidence retrieval, memory, AI routing, and a responsive single-page UI. It is not a diagnostic engine: intelligence and recommendations must preserve uncertainty and must not replace a clinician.

The repository is a two-service project:

- `backend/`: FastAPI API, deterministic health reasoning, Supabase persistence, RAG, AI routing, and pytest coverage.
- `frontend/`: Next.js 15 / React 19 client with Tailwind CSS 4.
- `supabase/migrations/`: chronological PostgreSQL/Supabase schema and RLS migrations.
- `docs/`: the clinical review packet, schema proposals and brand image.

The backend is currently a large endpoint coordinator (`backend/main.py`) that composes many focused analysis modules. Read those modules when an endpoint's behavior is not obvious from its response shape.

## Environment configuration

Backend secrets and policy flags live in `backend/.env`:

- `SUPABASE_URL`
- `SUPABASE_SECRET_KEY`
- `BUBBLES_FRONTEND_ORIGINS` — defaults to localhost HTTP origins and is used by FastAPI CORS middleware
- `ALLOW_PAID_AI` — defaults to `false`
- `ALLOW_KEYLESS_AI` — defaults to `false`
- `ALLOW_KEYLESS_HEALTH_DATA` — defaults to `false`
- `AI_REQUEST_TIMEOUT`, `AI_MAX_RETRIES`, `AI_RETRY_BACKOFF_MS`
- Optional verified free-provider credentials/models listed in `backend/.env.example`

Frontend variables live in `frontend/.env.local`:

- `NEXT_PUBLIC_API_URL` — defaults in code to `http://127.0.0.1:8000`
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`

The frontend must not silently contact placeholder Supabase credentials. `frontend/lib/supabase.ts` currently creates a client with placeholder fallback values; the login page checks `isSupabaseConfigured`, but the dashboard must also gate Supabase-backed initialization and display a configuration error instead of attempting auth/database calls.

Never commit `.env` files, real health records, API keys, `node_modules`, `.next`, caches, or generated bytecode. The repository's ignore rules exclude these artifacts.

## Backend architecture

### Entry point and HTTP surface

`backend/main.py` owns FastAPI app construction, CORS/security headers, authentication, endpoint registration, and orchestration. Its major areas are:

- `/health` — unauthenticated service health.
- `/chat` — authenticated, backend-owned conversation persistence and response generation.
- `/chat/feedback` — thumbs up/down on a saved Bubbles reply (POST to rate, GET `?message_ids=` to read back). One signed `doc_store` document per reply with a fixed reason list and no free text; owner-checked, no schema change.
- `/profile`, `/memory/diagnostics`, `/personalization/overview` — identity and memory surfaces.
- `/intelligence/*`, `/bubbles/intelligence`, `/intelligence/deep` — bounded health-analysis views.
- `/insights/weekly`, `/patterns/analyze` — longitudinal summaries.
- `/rag/search`, `/knowledge/health` — evidence retrieval and corpus status.
- `/health-events/*/confirmation`, `/memory/promote` — explicit user confirmation and promotion paths.
- `/companion/daily` — personalized daily context.
- `/medical/summary`, `/doctor/timeline`, `/doctor/prepare` — care-preparation views.
- `/safety/escalate`, `/privacy/*`, `/ai/*` — safety, privacy, and routing diagnostics.
- `/intelligence/body-systems`, `/intelligence/living-map`, `/intelligence/next-actions` — organ, living-signal, and next-action views.
- `/admin/*` — the admin portal API (`admin_api.py`), gated in the middleware by `_admin_gate` before routing (fresh sign-in, two-step `aal2`, `BUBBLES_ADMIN_USER_IDS`); everyone else gets the same 404 as a missing path. See `docs/admin/README.md`.
- `/evidence/grounding`, `/interventions/select`, `/evaluation/*`, `/multimodal/*`, `/agent/plan`, `/interop/fhir/*` — governance and interoperability helpers.

The API convention is a Bearer access token on protected routes, JSON request bodies where state or a window is supplied, bounded `days` values, and FastAPI validation errors for malformed input. Keep request windows bounded and preserve explicit `status: "success"` responses for UI normalization.

### Authentication and persistence

`backend/supabase_client.py` is the server-side Supabase client. Protected endpoints authenticate with `supabase.auth.get_user(token)` and scope queries to the authenticated user. The trusted backend writes canonical health and chat data; browser clients must not write AI-derived health records.

`backend/main.py` provides:

- `_ensure_conversation` for owner-scoped conversation resolution.
- `_persist_chat_message` for the single backend-owned chat-message persistence path.
- `client_message_id` idempotency for retries.
- `_get_user_health_events` and `_bounded_events` for bounded event reads.

Chat persistence is backend-owned. The browser sends the optional conversation ID and a client-generated idempotency key. A reused key with different content must return a conflict rather than silently changing the logical message.

### Safety and AI routing

`backend/safety_engine.py` is deterministic and runs before generative AI. RED is a hard gate: urgent responses are generated without sending the message or health context to a provider. AMBER routes to cautious guidance without diagnosis or false reassurance. GREEN is not proof that no emergency exists.

`backend/ai_provider.py` implements the free-provider allowlist and provider error handling. `backend/ai_orchestrator.py` applies policy and budget routing. The default policy is `$0 AI`: paid routing and keyless routing are disabled, and keyless health-data routing is disabled. Do not enable paid or keyless health-data routing without explicitly revisiting policy, privacy, and provider terms.

### Operational telemetry and caches

`ops_telemetry.py` records metadata-only events (api, ai_attempt, ai_reply, error, audit) with a per-request id; `record()` drops any field not on its kind's allow-list and never raises, and a daemon thread writes them to `bubbles_ops_events` (memory-only until that migration is applied). Never add message text, prompts, replies, user ids, raw paths or error messages to an event. `ttl_cache.py` holds the server caches (sign-in 30 s, consent 5 min, profile-sync flag 1 h); any new cache must be user-scoped or hold no user data, and must define its invalidation. Admin-editable settings are only those in `admin_settings._spec()`.

### Health data and reasoning

The event pipeline is split across focused modules:

- `health_event_pipeline.py` prepares LLM-proposed events.
- `health_event_projection.py` projects confirmed events into canonical structures.
- `context_engine.py` builds user context.
- `memory_*.py` handles explicit facts, L0-L4 memory levels, knowledge graphs, and diagnostics.
- `pattern_engine.py`, `weekly_insights.py`, `health_state_engine.py`, `learning_engine.py`, and `longitudinal_health_analysis.py` produce bounded observations and trends.
- Domain modules cover nutrition, cycle, sleep/recovery, fitness, body systems, medical records, doctor preparation, medications, mental/social wellbeing, and interventions.

The LLM proposes health events; the backend validates and persists them. User confirmation controls promotion from extracted events to persistent memory. Missing data must be surfaced as a gap, not interpreted as healthy.

**Association engine** (links between what a person logs): `correlation_core.py` (Spearman, permutation p, Benjamini-Hochberg, never causal) -> `association_insights.py` (`PAIRS` is a short curated list of links with fixed wording; one false-discovery correction covers all of them, so every added pair makes the engine stricter) -> `association_loader.py` (loads sleep, mood, activity, drinks, food, symptoms, heart rate and cycle phase as daily series; missing is never zero; 30-minute in-process cache). It serves `GET /wellness/associations` and feeds at most three derived sentences into chat context via `chat_block()`, which never waits: a cold cache is warmed in the background for the next message. To add a link: add a row to `PAIRS` (and a series to the loader if needed), then a test.

### RAG and evidence

`supabase/migrations/20260915_rag.sql` defines the global/private RAG document and chunk model, source metadata, FTS, pgvector, and `rag_hybrid_search`. Retrieval uses lexical and semantic ranks with reciprocal-rank fusion. The search function is callable by authenticated users but is not a trust boundary: application code must still enforce document scope and user ownership. Clients read evidence; they do not ingest or mutate the corpus.

Retrieval layers in `rag.hybrid_search` (each deterministic, each with an off switch, all measured by `backend/eval_retrieval.py` against the live store, 65 cases in `tests/eval/retrieval_cases.jsonl`; re-run it after any ingest or ranking change):

- `query_expand.py` (`RAG_EXPAND=0` off; `RAG_EXPAND_MODE=or|embed|and`, default `or`): adds the English medical word for lay / Hinglish / Hindi terms. The meaning search gets the words; the keyword search gets them as extra OR alternatives so it never gets stricter. Ambiguous words (sugar, gas) expand only with a health cue; no diagnosis words are invented.
- `rag_links.py` (`RAG_LINKS=0` off): `LINK_DOCS` names stored, verified documents that explain how two areas affect each other (sleep and mood, exercise and sleep, cycle and mood...). `python rag_links.py --apply` adds a `link:<a>-<b>` topic tag to them (additive, idempotent; no new text is written). A question that names both areas pulls those documents first, and `/wellness/associations` shows them as "what published sources say" under each pattern. To cover a new link: add it to `LINK_DOCS` and `LINK_QUERY`, run the tagging, add an eval case.
- Last measured: recall@5 1.00, recall@1 0.85 (65 cases); with expansion but without links: 0.94 / 0.74 on the same set.

### Database ownership model

The canonical schema contains 20 tables organized around auth/profile identity, conversations/messages, extracted and canonical health events, memory, RAG, nutrition/cycle/fitness observations, medical records, organ assessments, sharing, RL feedback, and governance/audit records. RLS policies should read as the primary data-access contract. New tables should enable RLS, define owner/user-scoped reads, and reserve writes for the trusted backend unless the UI explicitly needs a user-owned write.

## Frontend architecture

The frontend is a Next.js 15 App Router project (React 19, Tailwind 4) with one route per area. The public front door is the scroll-story landing; everything else is the signed-in app.

- **Landing (`frontend/app/landing`, rendered by `app/page.tsx` as `<Landing/>`):** a React Three Fiber story with a moving 3D Bubbles host, a 3D spine and ten chapters. Do not delete or replace it. Its building blocks: `atmosphere/` (chapter colour script in OKLab, sky shader and CSS fallback), `bubbles/` (soap bubbles), `post/` (bloom and grade, full tier only), `perf/tier.ts` (static, lite and full tiers with a frame monitor), `story/` (scroll director, store, chapter rail, Pause motion) and `world/` (scene, spine, lights). Reduced motion and no-WebGL visitors get a complete static page. Contrast, dash and claim rules are enforced by tests (`atmosphere/contrast.test.ts`, `accessibility.test.ts`).
- **Signed-in app:** seven sections (Today `/dashboard`, Talk `/companion`, Patterns `/insights`, Track `/health` plus the tracker pages, Cycle `/cycle`, Fitness `/fitness`, Care `/care`) and Me (`/profile`, `/settings`). `components/Navigation.tsx` defines `SECTIONS` and `ME`; each page mounts `SectionTabs` through the two shells (`components/hub/HubKit.tsx` and `components/tracking/kit.tsx`). The Ctrl+K "Ask or jump" palette is `components/AskBubbles.tsx` with `components/commandPalette.ts`.
- **API boundary:** `useApi().fetchBubbles` (in `components/Providers.tsx`) is the only way to call the backend. It removes trailing slashes, refuses insecure HTTP from HTTPS pages, applies a timeout, retries only network failures and classifies failures through `app/lib/connection.ts`. Never call `fetch(`${API_URL}...`)` directly.
- **Auth:** `lib/supabase.ts` (configuration guard, dev-only preview flag), `app/login/page.tsx` (sign in, sign up, email link, resend confirmation), `app/callback/page.tsx`, `lib/auth-links.ts` (confirmation links always return to the real site, links that land on the wrong page are forwarded to `/callback`) and `lib/auth-errors.ts` (plain-language errors, no account-enumeration leak). `next.config.ts` redirects the two old production Vercel addresses to the real site; the API only accepts requests from `https://heybubbles.in`.
- **Privacy veil:** `components/PrivacyVeil.tsx` blurs anything marked `data-private` when the tab is hidden or when Hide is pressed (opt-in in Settings). Never mark safety or urgent content.
- **Dev-only UI preview:** `NEXT_PUBLIC_UI_PREVIEW=1` with `backend/preview_server.py` (`BUBBLES_PREVIEW=1`, fake database, token `preview`) shows signed-in screens with synthetic data. The flag folds away in production builds; never set it on Vercel or Render.
- **Admin console (`frontend/app/admin`):** one route with tabs (`?tab=&range=&request=`), its own light header (not HubPage), polling only. Any non-200 from `/admin/me` or a later 404 renders the ordinary not-found page. Logic and wording in `app/admin/format.ts` (tested).
- **Conventions:** copy is plain and calm, no em-dashes in visible text, no diagnosis or dosing language, missing data is shown as a gap and never as healthy, and every button must do something real. Pure logic lives in small modules with tests next to them (`app/lib/*.ts`, `app/<area>/*.ts`); components stay thin.
